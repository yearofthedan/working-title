# Commits and merges

**Audience:** anyone landing a change here.
**Purpose:** what a change's messages look like, on the branch and in the log.

- **The issue number leads the subject** of a pull request title and of every commit: `15: Check claims against their docs`. Merges are the exception, since `Merge branch 'main' into …` has its own shape.
- **A change reaches `main` through a pull request, squash-merged**, so the pull request title is the message that lands. [The squash merge message](https://docs.github.com/en/pull-requests/reference/pull-request-merges#merge-message-for-a-squash-merge) is generated by GitHub and can be edited before it lands, and [the squash settings](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests) choose what the default message is. The commits on the branch are read in the pull request while it is reviewed, so they carry the issue number too.
- **The pull request body names who wrote it**: the tool and model that did the work, and the models that reviewed it. The body outlives the branch; the merge carries the title alone.
- **The repository settings carry part of it**: squash and rebase merging are allowed, merge commits are refused, and the squash message defaults to the pull request title — the setting that makes the title above the message that lands.
- **The ruleset on `main` carries the rest** ([the ruleset](https://github.com/yearofthedan/working-title/rules/24845766), [#16](https://github.com/yearofthedan/working-title/issues/16)): a pull request, squash only, and the `check` job required by name. [A ruleset sets the merge types a branch accepts and the checks it waits for](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), so squash is the only method `main` takes and the branch's commits never reach it as they are.
