# Working with the builder

A call the builder has to answer goes to them alone, and the work waits for it. State it in a message of its own, build nothing that assumes the answer, and never let it sit as a clause inside a status report — a question buried in a report is not a question. Ask before posting to an issue or creating a pull request on their behalf: a question posted there answers it for them.

A question or an aside is answered, not immediately acted on. A correction — the builder saying something was got wrong — stops the action it names, not the work. Say in a line what was got wrong, then wait for the builder's word on what to do: repairing, reverting, re-running or tidying on your own initiative answers for them.

A change in how you work lands as a line in a file, not as a promise.

# The standards are followed

Every change follows the standards in `docs/standards/`, [indexed here](../docs/standards/README.md): the one that governs a file is read before the file is written, not after a review cites it.

# What you assert

A claim about this repository's own files — which change last touched one, what a file holds — is read from the repo, with the file or the command beside it.
